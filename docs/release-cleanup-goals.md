## 시작 전 관문

1. **git 저장소 안에서 돌린다** — 루프는 커밋으로만 진행을 남긴다. 커밋이 없으면 중단 시점의 작업이 사라진다. ✅ (fish-log 저장소, `master`)
2. **격리 — 커밋은 파일을 지정해서 한다.** 2026-08-30 확인 시점 작업 트리에 **선행 변경 119건**이 있다
   (미추적 117건 + 추적 수정 2건: `android/app/build.gradle`, `pwa_build_request.json`). 이 셋은 GOAL 과 무관하다.
   `git add -A` 를 쓰지 않는다 — 무관한 선행 변경이 GOAL 커밋에 섞이면 되돌리기 단위가 깨져
   「커밋으로 진행을 남긴다」는 전제 자체가 무너진다. 각 GOAL 은 자기가 건드린 경로만 `git add` 한다.
   세 GOAL 은 서로 다른 파일을 건드리며 상호 의존이 없다.
3. **처음 두 바퀴는 수동** — GOAL-1, GOAL-2 를 사람이 직접 시키고 기록을 읽는다. 프롬프트 결함은 1~2 바퀴에서 대부분 드러나며, 그 상태로 자동 루프를 걸면 결함이 GOAL 수만큼 복제된다. GOAL-3 만 `/loop` 로 돌린다.

## 공통 실행 프로토콜 (모든 GOAL 동일)

1. **읽기** — ⓪ 의 문서를 지정 범위까지 읽는다. INBOX 미처리분이 있으면 그것부터.
2. **전제부터 실측한다** — 체크리스트가 적어 둔 원인·해법은 **가설이지 사실이 아니다.**
   고치기 전에 그 전제가 지금도 참인지 코드나 화면으로 확인한다.
   두 바퀴 모두 전제가 틀렸다: GOAL-1 은 「에러가 catch 로 온다」가 전제였으나 Firestore 는
   오프라인에서 캐시로 **성공 응답**했고, GOAL-2 는 「CSP 가 막는다」가 전제였으나 CSP 자체가 없었다.
   전제를 확인하지 않으면 없는 병에 약을 짓는다.
3. **하나만 구현** — 한 바퀴에 GOAL 하나. 여러 항목을 얕게 건드리면 검증도 커밋도 단위가 무너진다.
3. **검증 게이트** (전부 통과해야 다음 단계):
   - `npm run lint` — 에러 0
   - `npm test` — 전체 통과 (신규 로직은 유닛 테스트 동반 필수)
   - `npm run test:e2e` — 해당 GOAL 관련 스펙 통과. 개수 변화만 보는 얕은 단언 금지 — 실제 내용을 단언
   - `npm run build` — 에러 0
   - **직접 확인** — 화면에 보이는 것이면 실행해서 눈으로 본다(스크린샷 1장을 증거로). 코드가 도는 것과 화면이 멀쩡한 것은 다른 문제이며, 자동 검사는 「돌아갔다」까지만 증명한다.
     **스크린샷에 판정 대상이 실제로 담겨 있어야 한다** — 대상을 화면 안으로 스크롤하고 이 앱의 실제 사용 폭(390px)으로 찍는다. GOAL-1 에서 데스크톱 폭으로 찍어 배너가 뷰포트 밖으로 밀린 채 「확인함」이 될 뻔했다. 담기지 않은 스크린샷은 증거가 아니다.
4. **합격 기준 한 문장** — GOAL 정의의 수용 기준을 한 문장으로 자문한다. **통과하지 못하면 커밋하지 않는다.** 이 문장이 없으면 「실행되면 완료」로 판정이 무너진다.
5. **실패 시** — 수정 후 재검증, GOAL 당 최대 3회. 3회 실패 시 즉시 중단하고 `GOAL-N BLOCKED: <사유>` 보고 (무한 재시도 금지)
6. **커밋** — 검사를 통과하면 **검토보다 먼저** 커밋한다. 중단은 예고 없이 오고 스테이징은 커밋이 아니다 — 검토 후 고칠 것이 생기면 커밋을 하나 더 붙이면 된다. Conventional Commits.
7. **상태표 갱신** — 상태를 DONE 으로, 증거 열에 커밋 해시 + 검증 결과 한 줄
8. **완료 토큰** — `GOAL-N DONE` 출력

## GOAL 정의

### GOAL-1 · rankingService 실패 원인 구분

- **범위**: `src/services/rankingService.ts` 238~241행의 catch, 그리고 그 결과를 소비하는
  `src/app/ranking/page.tsx` 62~76행.
- **현상**: 서비스가 timeout(210행에서 던지는 `ranking fetch timeout`)과 Firestore 권한 오류를
  **같은 `getEmptyRanking(category)` 로 삼킨다.** 성공 모양의 값이 돌아오므로 페이지의
  `catch`(68행)는 이 경로에서 절대 실행되지 않고 `setError` 는 죽은 코드다.
  사용자에게는 **권한 실패와 「아직 기록 없음」이 똑같이 보인다.**
- **수용 기준(한 문장)**: 「랭킹이 비어 보일 때, 그것이 데이터가 없어서인지 불러오기가 실패해서인지
  화면과 로그 양쪽에서 구분되는가?」
- **검증**: 유닛(vitest) — timeout 주입 시와 권한 오류 주입 시 반환값이 서로 다르고,
  둘 다 「데이터 없음」과도 다름을 단언한다. 얕은 단언(호출 횟수) 금지.
  직접 확인 — 랭킹 화면에서 실패 상태의 안내가 빈 상태와 다르게 보이는지 눈으로 본다.
- **회귀**: 정상 경로에서 `isRealData: true` 랭킹이 그대로 나오는가. 빈 데이터(aggregates.size === 0)는
  여전히 오류가 아닌 빈 랭킹으로 처리되는가.

### GOAL-2 · Windy iframe 배포 환경 렌더 확인

- **범위**: `src/app/page.tsx` 438행의 iframe(`https://embed.windy.com/embed.html?...`),
  필요 시 `next.config.ts`.
- **전제 검증 우선**: 체크리스트는 CSP 추가를 「권고」하지만, 실측 결과 **이 프로젝트에는 CSP 가 없다**
  (`next.config.ts`·`vercel.json`·`firebase.json`·미들웨어 어디에도 없음).
  없는 CSP 를 이유로 차단을 단정하지 않는다 — **먼저 라이브에서 iframe 이 실제로 렌더되는지 본다.**
  렌더되면 이 항목은 「재현되지 않음」으로 닫고 CSP 를 추가하지 않는다.
  CSP 가 없는 곳에 부분 CSP 를 넣으면 없던 제약이 생겨 다른 임베드를 깨뜨릴 수 있다.
- **수용 기준(한 문장)**: 「배포된 홈 화면에서 Windy 지도가 실제로 보이는가, 그리고 그 판정이
  추측이 아니라 화면과 콘솔로 뒷받침되는가?」
- **검증**: `npm run build` 에러 0. 직접 확인 — 라이브 URL 홈에서 iframe 렌더 여부를 눈으로 보고
  콘솔에서 CSP 차단 메시지 유무를 확인한다(스크린샷 1장).
  차단이 확인된 경우에만 `next.config.ts` 에 `frame-src https://embed.windy.com` 을 더하고 재확인한다.
- **회귀**: CSP 를 추가했다면 다른 외부 리소스(Firebase·Naver·YouTube)가 여전히 로드되는가.

## ③ 규칙 작성 규약

이 문서에 규칙을 쓸 때는 **금지문 뒤에 근거 한 줄을 붙인다.**
「하지 마라」만 적으면 우회로를 찾고, 「이러면 이렇게 된다」를 적으면 그 이유를 지키려 한다.
이 문서의 모든 규칙 줄이 이미 그 형태다. 새 규칙도 같은 형태로 추가한다.

## 루프 안전 (중앙 규칙 준수)

- 반복 상한: 루프 1회 = GOAL 1개, **최대 3회**. 무제한 반복 금지 — 상한 없는 루프는 실패를 계속 신호로 바꾼다.
- GOAL 당 수정 재시도 상한 3회 — 초과 시 `GOAL-N BLOCKED` 보고 후 정지.
- 종료 토큰: 전 GOAL DONE 시 `ALL GOALS DONE`, 차단 시 `GOAL-N BLOCKED: <사유>`.
- 상태는 이 문서의 상태표가 단일 진실.
- 자동 재시작은 쓰지 않는다 — 이 파일럿은 3바퀴짜리 유한 작업이라 재시작 장치가 필요 없고,
  없는 편이 중앙 규칙 위반 여지도 없다.
